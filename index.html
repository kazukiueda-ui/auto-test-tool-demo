    DBデータ更新の検証（設定は接続だけ・クエリ任意）
    
自動発見モード（既定）：「設定」画面でDB接続を保存しておくと、テスト実行の前後でDBを丸ごとスナップショットし、変化したテーブル・行を自動で検出します。クエリやテーブルの指定は不要です（read-only・動的値は正規化）。
初回は全テーブルを対象にし、結果画面で「★ DBデータ更新を期待値に承認」すると、以降は更新のあったテーブルだけを対象にして軽量化＆回帰判定します。

    
下の検証クエリ（任意・上級者向け）は、特定の行だけを期待値化して毎回チェックしたい場合に使います。通常は不要です。無視列に id/created_at 等を入れると誤検知を防げます。

DBデータ更新の検証（接続設定）

   
テスト実行後のDBの状態を、1回目(期待値)と比較して「データ更新が正しいか」を確認します。認証情報は環境変数に置き、ここには参照名だけ保存します（read-only運用を推奨）。検証クエリは③テストケース管理で設定します。

   

    
    
    
   

   

    
    
   

   
対象を指定するとそのテーブルだけ、除外は常に無視します（ログ/セッション等のノイズ用）。承認後の「更新テーブルのみ」絞り込みは、この範囲内でさらに効きます。

   
MySQLは npm i mysql2、PostgreSQLは npm i pg が必要です。接続文字列は例）mysql://user:pass@host:3306/dbname を環境変数に設定してください。

   
  

  

  

   
回帰検知の通知（Slack / Teams）

    CI連携（cron / GitHub Actions から実行）
    
非対話でCLIまたはAPIから実行できます。差分があれば終了コード1（CIで失敗検知可）。

    
# CLI（cron/GitHub Actions のステップに）
npx att ci-run --project <pid> --suite <suiteId> --after https://n1.example.com/ --json

# API（トークン認証時は ?token= 併用）
curl -X POST "$HOST/api/ci/run?project=<pid>" -H 'Content-Type: application/json' \
  -d '{"suiteId":"<suiteId>","after":"https://n1.example.com/"}'

業務ドメイン別テスト設計ノウハウ（ツリー管理）

   
共通（一般的なWebシステム）→業務システム→業界別の分類ツリーで管理します。各業務を開くと重点観点・境界値・異常系・テストデータ設計のノウハウが表示され、これが探索・AIレビューへ注入されます（テスト専門家＋業務専門家の知見）。プロンプト欄を編集するとその業務だけ上書きできます。「＋ 業務を追加」で独自業務も追加可能（ヘッダの選択にも反映）。
